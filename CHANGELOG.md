# Changelog

All notable changes to logler will be documented in this file.

## [Unreleased]

Requires Python 3.12 or later. One compiled wheel per platform serves 3.12, 3.13, 3.14 and later (the extension is built against CPython's stable ABI).

### Upgrading from 1.3

- **A log file that cannot be read raises Python's own file errors.** `logler.investigate` functions raise `FileNotFoundError`, `PermissionError` or `IsADirectoryError`, with `.filename` set, where they raised a bare `RuntimeError`. Code that caught `RuntimeError` for a missing file no longer catches it.
- **Exit code 2 for a file a command cannot open, read or write.** The `llm` commands print `<file>: <reason>` and exit 2, where they printed "Internal error" and exited 3. `view`, `stats` and `investigate` print `❌ Error: <file>: <reason>` and exit 2, where `view` and `investigate` printed Python's own text (`[Errno 21] Is a directory: 'app.log'`) and exited 1, and `stats` printed a traceback. The `llm` error object also has a `file` key with the file's name; an error that names no file has no such key. `watch` refuses a directory that is missing or is a file with exit 2.
- **A line with no level is `UNKNOWN` everywhere**, and it is counted in every count by level. The Python API gave such a line the text `NONE`.
- **A `.logler/formats.yaml` or `.logler/correlations.yaml` that cannot be used stops the command.** Broken YAML, a schema error or a regex the engine cannot compile is exit 2 with the file and the problem (`FormatFileError`, a `ValueError`, from the API). Before, the file was skipped in silence and the log was read with the built-in detection.
- **A `timestamp_format` logler cannot read stops the command** like any other unusable formats file (exit 2, `FormatFileError`), naming the format and the word: a zone name (`%Z`), a word read in the machine's language (`%a`, `%A`, `%c`, `%x`, `%X`, `%p`), any other word outside the list in `docs/CONFIGURATION.md`, or a format without a year, a month and a day (`%H:%M:%S`). It was accepted and never used.
- **`llm sql` and `Investigator.sql_query` query the same `logs` table.** Its `timestamp` column is a `TIMESTAMP` in both, and the columns come in one order. A query written for the command's old text timestamps may need a cast removed.
- **A line number the file has no entry for is the caller's error.** `get_context()` raises `ValueError` (`LineNotFoundError`) with `<file>: no entry at line N`, where it raised `RuntimeError`, or `OverflowError` for a negative line. `llm context` exits 2 with that text, where it exited 3.
- **A `representative` sample comes back in file order.** It was grouped by level.
- **`--query` is one regex, matched without regard to letter case, against the whole line as written in the file and against the message read from it.** In `search` it was plain text looked for in the message only, and a line that shared one whole word with the query was a result too, ranked lower: `--query "connection timeout"` no longer finds `connection refused by peer` (`timeout|refused` asks for either). A JSON line is matched whole, so `--query "A-17"` finds a line whose `order` field is `A-17`, and a key name such as `level` matches every JSON line. `--exclude-query` ignores letter case in `search`, as it did in `emit`; it looks at the line and the message, as before. `emit` looks at the same text for both flags as `search` does; it reads the pattern with Python's `re`, `search` with Rust's engine (the reference lists where they differ).
- **Every result of a query has `relevance_score` 1.0, and results come in time order**, as without a query. The key stays; it was 1.0, 0.7 or a word-overlap fraction, and results were ordered by it. `limit` takes the first results in time order.
- **A pattern that is not a regex is the caller's error.** `search`, `Investigator.search` and the other API calls that take `query` or `exclude_query` raise `InvalidPatternError` (a `ValueError`) with `Invalid query pattern "(": unclosed group`, where `search` raised `RuntimeError` for `exclude_query` and read a bad `query` as plain text; `llm search` and `llm emit` exit 2 with that text, where `llm search` exited 3.
- **A line that is empty or holds only white space is not an entry, anywhere.** `search`, `sql`, the summary and every count by file, level, thread or entry count agree: a file of `a`, an empty line, three spaces, a tab and `b` has 2 entries, not 5 (the engine, `view`, `stats` and the five `llm` commands that skipped an empty line themselves used three different rules). White space is what Python's `str.strip()` removes, a line of `\r` or a no-break space included. A line number is still the line of the file: `b` is line 5, and a blank line's number is not reused. `get_metadata()` `lines` and `quick_summary()` `total_lines` still count the lines of the file; the new keys `entry_count` (the field `FileMetadata.entry_count` of `logler.models`, which nothing filled before) and `total_entries` count its entries, the level counts add up to them, and `error_rate` is a share of the entries. `llm format test` `total_lines` counts the lines it tested, and no longer counts a line of spaces. `get_context()`, `search` `context_lines` and `llm context --before/--after` count entries, so the entry before `b` is `a`. `LogReader.tail()`, `search()` and `read_lines()` and the followed `view` skip a blank line.
- **`llm emit --pretty` is removed.**
- **`llm emit` exits 1 when nothing matches**, like every other `llm` command. It exited 0.
- **`LogReader.tail(0)` gives no lines.** It gave the whole file.
- **The `export` value of `llm export` is the output of `export_to_jaeger`, `export_to_zipkin` or `export_to_otlp`.** Jaeger: each span names its service through `processID` and `processes` holds one process per service, where every span carried an inline `serviceName` and `parentSpanId` under one process `p1`; the parent is in `references`, ids are `spanID` and `traceID`, the operation is `operationName`, times are microseconds, and the keys `total`, `limit`, `offset` and `errors` are gone. OTLP: one `resourceSpans` entry per service, times are decimal text of nanoseconds, and a root span has no `parentSpanId`. Ids change in every format (see Fixed), and a span with no service is under `logler-export`, where it was `unknown`.
- **Fields of the pydantic models in `logler.models` follow the API's names:** `FileMetadata.lines` (was `line_count`) and `log_levels` (was `level_distribution`), `PatternMatch.occurrences` (was `count`), `SamplingResult.samples` (was `entries`). `SpanNode.entry_ids` holds the entries' ids as text.
- **Importing logler never starts a build.** Without the compiled extension the import warns once and says how to build it.
- The unused HTTP server, the second command-line program and the old web back end are deleted from the repository. None of them was in the published package.

### Fixed

- **An all-zero trace, span or parent span id is no id.** OpenTelemetry writes `00000000000000000000000000000000` and `0000000000000000` for a line made outside a span, and W3C trace context and B3 call them invalid. An id of 16 or 32 characters that is only `0` is now absent on the entry, in JSON, logfmt, plain and custom formats, so those lines no longer form one trace node, children no longer link across traces, and `ids`, `follow_thread`, `hierarchy` and `summarize` never take it for an id. A logfmt line still has the key in its `fields`, as it has every key of the line. Any other id is kept as written (`0012345678901234`, `00000042`, `0`).
- **A `--db` row's line holds its text as read.** The line was written with `\uXXXX` escapes for everything outside ASCII, so `--query 日本語` found the text in the message and not in a field beside it. A lone surrogate in a stored document (a cut emoji) is written as U+FFFD, as an invalid byte of a log file is: the engine read a row that held its escape as plain text, with no fields. A row is still one line.
- **One parser.** `logler stats`, the viewer and the `llm` commands `schema`, `summarize`, `sql`, `verify-pattern`, `emit` and `compare` parsed with a second parser that knew JSON and plain text only, so `summarize` and `search` could count the same file differently. Every command now parses with the Rust parser.
- **More level words and line shapes are read:** `NOTICE`, `SEVERE`, `EMERG`, `EMERGENCY`, `ALERT`, `PANIC`, `INFORMATION`, `ERR` and `CRIT`; a level in any letter case at the head of a line before a colon, after a leading timestamp, or alone in square brackets; a logfmt line that leads with a timestamp and a level keeps both.
- **A custom format applies in every command.** A format in `.logler/formats.yaml` reached only `Investigator.load_files()`. It now parses the files it names, file by file, in every command and API call, and its regex keeps every named group.
- **A custom format's `timestamp_format` is applied.** It was accepted and ignored, so `31.12.2024 23:59:58` or `10/Oct/2024:13:55:36 -0700` in a format's `timestamp` group had no time. The group is now read with the format's Python `strptime` words first (`%f` as a fraction of a second, `%z` as `+0900` or `+09:00`, month names in any letter case, no zone read as UTC), and in the shapes logler knows when it does not fit. Two formats with one regex and different `timestamp_format` values read their files apart. `LogParser`, `PyLineParser` and `PyInvestigator.load_files_with_config` take a `timestamp_format`. A file whose format has no `timestamp_format`, and every file without a custom format, is read as before.
- **`llm format test` shows the time the engine reads.** Each matched line has `timestamp` (ISO 8601 or null) and `engine_matched`, and the summary has `timestamp_format`, `matched_lines_with_timestamp` and `engine_unmatched_lines`; a regex the engine cannot compile is exit 2. The regex is looked for anywhere in a line, as the engine looks for it; it was tied to the start of the line, so a regex without `^` showed lines as unmatched that every command read. `--name` takes a format of the formats file before a built-in of the same name.
- **A `timestamp_format` on a regex with no timestamp group stops the formats file** (exit 2, `FormatFileError`), naming the format, its groups and the names to use: the engine reads `timestamp`, `time`, `ts` and `datetime`, so the field could never be used.
- **`llm format validate` accepts `time`, `ts` and `datetime` as the timestamp group**, as the engine reads them; it asked for `timestamp` only.
- **A log with a byte that is not UTF-8 can be read.** One Latin-1 byte failed every command that loads the file. Such a byte is now shown as U+FFFD. A byte-order mark at the start of a file is not part of line 1.
- **Line numbers and line text agree between commands.** Every command cuts a file into lines the same way: a line ends at a newline, a carriage return right before it is dropped, and nothing else is trimmed.
- **`--last 30m` works.** It ended every command that takes it with an internal error. It means from that long ago until now.
- **Time bounds are compared as times.** `llm summarize --after 2024-01-15T09:00:00Z` dropped every line of that day; `sample`, `correlate` and `diff` had related faults. A line with no time is inside any bounds, in every command.
- **A zone written after a space is read:** `2024-01-15 10:00:00 +0900 INFO started` was read nine hours off.
- **A bad level word is exit 2**, not an internal error, and a duration too long for the calendar is exit 2 with the flag named.
- **A time is written one way** by every `llm` command, with the digits of a second that the log has; `llm metrics --bucket` writes its bounds the same way.
- **A followed log shows every line once and whole**, under its line number in the file (`logler view --follow`, `LogReader.tail(follow=True)`).
- **`LogReader.tail(n)` reads only the end of the file.** It read the whole file; a very long single line took time that grew with the square of its length.
- **`logler llm sql "SELECT now()"` returns the time.** It failed for want of `pytz`, now a dependency.
- **`logler investigate`** prints an error it cannot recover from on stderr and exits 1, where its error handler raised.
- **`logler.__version__`** is the installed version; it said 1.1.2.
- **A logfmt value `nan` or `inf`** no longer ends a whole search with a panic.
- **Finding the numbers in a message is linear in its length.** A message holding one unbroken word of 50,000 characters took about a minute to scan.
- **A request tree counts each log line once.** A span under a parent with several log lines reported each of its own lines once per line of the parent, in `entry_count`, `error_count`, `level_counts` and `entry_ids`.
- **A `representative` sample has the size that was asked for.** `smart_sample(strategy="representative", sample_size=10)` could return 9 entries.
- **The same command on the same files prints the same output on every run.** `llm hierarchy`, `correlate`, `ids`, `schema`, `metrics` and `export` gave lists and map keys in another order from run to run, `schema` could show another hundred thread patterns, and `export` gave other span ids; `compare_threads`, `compare_time_periods`, `trace_request`, `detect_correlation_chains`, `diff_hierarchies` and `ThreadTracker` did the same with their lists. Files are now read in order of path, map keys are written sorted, ties in a ranked list break by name, nodes of a request tree that start together come in the order of their lines, and a list taken from log lines keeps the order of first appearance.
- **The typed dicts in `logler.types` describe what the API returns.** `LogEntryDict` lacked `id`, `raw`, `format` and `parent_span_id`; `SearchResultItem` lacked `relevance_score`; `SearchResult` lacked `search_time_ms`; `ContextResult` lacked `related_threads`; `BottleneckInfo` lacked `node_name`; `PatternInfo` lacked `pattern_type`; `ExtractedIds` said its lists hold text where they hold `{id, count, first_seen, last_seen}`; `SearchResult` and `PatternResult` listed keys that are never returned; `MetricsFieldStats` listed its numbers as flat keys where `extract_metrics` returns them under `stats`. Every class is now total, a key returned only under a condition is `NotRequired` and says when, and each class is checked against the real output, keys and value types, in the test suite. The docstrings that showed the old shapes are corrected.
- **The context lines of a search result carry the same level text as every other entry.** With `--context` or `context_lines`, the entries before and after a match read `Info`, and null for a line with no level, where the match itself read `INFO` and `UNKNOWN`.
- **`analyze_bottlenecks`** ranks its secondary bottlenecks by self-time, as it ranks the primary one.
- **A count of matches is the total.** `search(output_format="count", count_only=True)` said 0 where the same search without `count_only` said 20, and `total_matches` of the `count` and `summary` formats was the size of the page when `limit` was given. It is now every match of the query.
- **A summary and a count describe every match.** `log_levels`, `by_level`, `by_file`, `unique_messages`, `top_messages` and `time_range` of the `summary` and `count` formats were counted from the entries returned, at most `limit` or 10,000, while `total_matches` was every match, so `llm triage` gave a file of 12,000 lines whose last 2,000 are errors an error rate of 0. The engine now counts them over every match; `limit`, `tail` and `offset` choose only the `sample_entries`. A message's `first_seen` and `last_seen` and the `time_range` are compared as times: a whole second, written with no fraction, came after a time later in that second.
- **Reading a thread does not break the tracker.** `ThreadTracker.get_thread()` replaced the thread's set of correlation ids with a list, so the next line tracked for that thread failed. It returns a sorted copy.
- **`trace_request()` names the services of a JSON log.** It read only a `service` field of the entry, which a JSON line does not keep there.
- **A trace export carries the log's own span ids and services, and is the same in every run.** `export_to_jaeger` and `export_to_zipkin` made every span id and trace id up at random, and `llm export` named every service "unknown". A span keeps the span id of its log entries when it is 16 hexadecimal characters (in lower case) and not all zeros, which OTLP and W3C trace context call invalid; any other id, such as `s-one` or a UUID, is replaced by a 16-hex id derived from it with SHA-256, and parent links follow. No two spans of one export share an id. The trace id is the identifier when it is 32 hexadecimal characters and not all zeros, else derived from it the same way (new optional argument `identifier=`). A span is under the `service` of its node, else under `logler-export`.
- **`llm export` uses the library's converters**, so its spans are valid in Jaeger, Zipkin and OTLP. It stripped and padded ids (`s-one` became `sone000000000000`, and two ids could become one), gave a Jaeger trace a single process, and its OTLP output named one service for every span and put a text time in `startTimeUnixNano`.
- **`ProjectedSearchResult` describes `search(fields=[...])`**, whose entries hold only the asked keys; `LogEntryDict` still describes a whole entry.
- A failed SQL load no longer leaves its temporary CSV behind.
- **A JSON line whose level is a number has a level.** pino and bunyan write 10 to 60 (10 TRACE, 20 DEBUG, 30 INFO, 40 WARN, 50 ERROR, 60 FATAL); syslog and GELF write 0 to 7 (0, 1, 2 FATAL, 3 ERROR, 4 WARN, 5 and 6 INFO, 7 DEBUG). Such lines were `UNKNOWN`, so `--level ERROR` found nothing in them. Any other number (35, -1, 3.5, 1e3) and a string of digits stay `UNKNOWN`, and a number that is not a level stays in `fields`. A level word beats a level number, whichever key holds it: `{"level": 30, "severity": "ERROR"}` is ERROR, as it was.
- **Syslog severities 1 and 2 are FATAL**, as `ALERT` and `CRIT` are: `<9>` and `<10>` gave ERROR. 3 stays ERROR.

### Changed

- **A long search no longer blocks the other threads of a Python program:** the engine releases the GIL while it works.
- **The built-in `postgresql` format's `timestamp_format` is `%Y-%m-%d %H:%M:%S.%f UTC`**, where it was `... %Z`: a zone name is not read, so the format reads a server that logs in UTC and leaves other zone names to the known shapes.
- **Parsing is faster:** a JSON line is parsed once (about 30% less time a line), and a plain line costs less than it did in 1.3. An entry's ID is a counter under a random prefix, still a UUID in the JSON, where it was a random UUID: a plain line takes about a third less time.
- **The `count` format, and `llm export`, are faster.** On 1,000,000 lines a count took a quarter of the time; `llm export` no longer reads every line a second time to find the services, and took a quarter of the time and three fifths of the peak memory.
- The unused Rust `ThreadTracker` (not the Python one) and the `dashmap` dependency are removed.
- The index reads each file once, in file order, with bounded memory per batch.

### Added

- **`analyze_thread_health()` returns each thread's level counts**, as its documentation said: `{thread_id: {"INFO": 3, "ERROR": 2, "total": 5}}`. It returned a note and one number. The counting is done once in the engine.
- **A node of a hierarchy names its service:** `service` is the `service_name` of the first of its entries that has one, or null.
- **`export_to_otlp()`** exports a hierarchy to the JSON form of OTLP traces, with the arguments of `export_to_jaeger` and `export_to_zipkin`.
- **Type information.** The package ships `py.typed` and a stub for the compiled extension, and is checked with mypy.
